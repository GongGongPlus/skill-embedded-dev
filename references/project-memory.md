# 工程记忆：带依据的本地档案

适用场景：跨会话/跨人接手同一块板、同一个固件工程时，避免每次从零重建上下文。原则：**记忆是本地证据索引，不是硬件验收记录，也不能替代会话压缩、代码回滚或真机验证**。

## 一、工程识别（只读）

在工程根目录及最多两层子目录、最多 400 个目录项内扫描标记：

- CubeMX `.ioc`；Keil `.uvprojx`；IAR `.ewp`；`CMakeLists.txt`；`Makefile`；`platformio.ini`；ESP-IDF `sdkconfig` / `idf_component.yml`。
- 芯片候选来源：`.ioc` 的 `Mcu.UserName`→`Mcu.Name`→`Mcu.PartNumber`（只取一个）；`.uvprojx` 的 `<Device>`。
- 多个不同芯片候选 → 标记 `ambiguous` 并列出候选，不擅自选；识别结果是**建议**，不是定论。
- 构建系统成功只说明能构建，不代表已烧录，更不代表硬件验收。这些限制必须随识别结果一起输出。

## 二、记忆的三类内容

1. **工程知识**：目标芯片、时钟、板级连接、外设分配、构建与烧录路径、已知限制。用于新会话快速进入状态。
2. **调试经验**：现象 → 证据 → 根因 → 修复 → 如何验证的闭环。必须可复现。
3. **任务交接**：当前进行到哪、下一步、未决问题、被谁/什么阻塞。

每条记忆必须包含：标题、内容、适用范围（scope）、证据等级、依据（source）、来源会话/操作、更新时间。没有依据的"已验证"不允许写入。

## 三、证据等级

- 已确认：必须有 `--source`（手册章节/寄存器页码/逻辑分析仪抓包文件/日志行号/官方例程路径）。写入时强制校验；但真实性仍由人和后续实验核实，记忆系统只负责不丢依据。
- 工程推论：写清推理链与前提。
- 估算：给出假设与误差范围。
- 待验证：写清验证方法。
- 数据不足：明确缺什么。

## 四、文件布局与版本

- `<工程>/.embedded-dev/project.json`：工程档案，建议提交 Git，便于团队共享。
- `<工程>/.embedded-dev/knowledge/state.json`：记忆库与锁状态，默认不提交 Git（可能含日志片段、内部路径）。
- 记忆库最多 200 条；状态文件上限 512 KB；超限拒绝写入而不是静默截断。
- 写入采用文件锁（创建独占锁文件，过期 10 秒、等待上限 3 秒）；两次读取之间状态版本变化时，写入方必须带 `--expected-version`，版本不符返回冲突（退出码 4），不允许覆盖。
- 删除记忆不物理抹除标题：保留"已遗忘条目标题"作为墓碑，防止同一标题重建后看起来像旧结论仍然有效；确需重建必须显式 `--allow-recreate`。
- 已经写进会话的历史内容不会被追溯抹除；忘记只影响后续注入。

## 五、读取策略

- 每次会话开始：输出工程档案摘要 + 最近 6 条记忆。
- 需要更多时按关键词检索标题/内容/scope/标签（中英子串匹配，无外部服务、无语义索引），只把命中片段放进上下文。
- 不要一次性把所有记忆倒进上下文：记忆的目的之一是节省 token，不是制造新噪音。

## 六、安全与边界

- 工程根目录之外的文件不扫描、不写入；固件路径必须在工程内；状态目录禁止符号链接。
- 不记录密钥、口令、无线凭据、个人隐私数据；日志片段只保留必要行。
- 记忆与事实冲突时，以直接观测/官方手册为准，并更新记忆而不是让两条记录并存。
- 记忆不能替代：会话压缩、代码检查点/回滚、构建产物校验、烧录回读、真机验收。它只是"上次我们知道什么、依据在哪"。

## 七、推荐用法

1. 接手：`embedded_dev.py memory detect --project <dir>` → `init`（写档案）。
2. 调试前：`show` 读档案与最近 6 条；`search` 查关键词（如 HardFault、I2C、DMA）。
3. 得出结论时：有依据的写 `已确认` 并给 `--source`；推断写 `工程推论`/`待验证`。
4. 交接：写一条任务交接记忆，说明进度、下一步与阻塞。
5. 证伪旧结论时：先记住新证据，再 `forget` 旧条目（保留墓碑），不要只删不改。
